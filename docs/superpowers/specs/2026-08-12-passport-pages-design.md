# 디지털 여권 화면 및 브랜치 통합 설계

## 1. 목표

로컬 `develop`의 7개 커밋을 기존 PR 브랜치 `fix/boarding-pass-final`에 안전하게 통합하고, 현재 Figma에서 추가된 디지털 여권 화면을 Mock 데이터 기반으로 완성한다. 실제 인증과 API 연동은 모든 화면이 완성된 이후 별도 작업으로 진행한다.

- Figma 파일: `aklj7UjNcG6PDFJVRU9JXv`
- 기존 랜딩 보정: `36:5237` `(48)보딩패스발급페이지`
- 신규 여권 상태: `36:5315`, `36:5409`, `36:5545`, `36:5684`

## 3. 브랜치 통합

`fix/boarding-pass-final`에서 로컬 `develop`을 일반 merge로 통합한다.

- rebase와 강제 푸시는 사용하지 않는다.
- 기존 PR #3과 보딩패스 커밋 이력을 유지한다.
- `develop`의 홈 시각 보정, 국가명 정렬, 위시리스트 탭 보정, API 문서와 Vercel 미러 설정을 보존한다.
- 보딩패스 라우트, MSW, API 베이스 URL 및 런타임 수정은 PR 브랜치 버전을 보존한다.
- 병합 직후 `npm run verify`로 기준선을 다시 확인한다.
- 실제 푸시는 변경·커밋 내역을 사용자에게 보고하고 승인받은 뒤에만 수행한다.

## 4. 라우팅과 사용자 흐름

신규 라우트는 `/boarding-pass/passport` 하나만 추가한다. Figma 프레임별로 별도 라우트를 만들지 않는다.

1. `/boarding-pass`의 `PASSPORT 확인` 버튼
2. 기존 로그인 확인
3. `/boarding-pass/passport` 진입
4. 좌우 버튼으로 여권의 네 상태 이동
5. 마지막 여행 기록 상태에서 히스토리 또는 티켓 시트 열기

`비행 종료`는 `/boarding-pass`로 돌아간다. 사용자는 랜딩의 `PASSPORT 확인` 버튼을 눌러 여권에 진입한다.

닫기 버튼은 시트가 열려 있으면 시트를 먼저 닫고, 시트가 없으면 `/boarding-pass`로 돌아간다. 브라우저 뒤로 가기도 정상 동작해야 한다.

## 5. 페이지 상태 구조

`PassportPage`는 다음의 로컬 상태만 가진다.

- `step`: `0 | 1 | 2 | 3`
  - `0`: 여권 커버, 진행률 25%
  - `1`: 프로필과 크레딧, 진행률 50%
  - `2`: 방문 스탬프, 진행률 75%
  - `3`: 여행 기록과 티켓 진입, 진행률 100%
- `sheet`: `null | 'history' | 'history-detail' | 'ticket'`

진행률은 `(step + 1) * 25`로 계산한다. 첫 단계의 이전 버튼과 마지막 단계의 다음 버튼은 비활성화한다. 캐러셀 라이브러리나 전역 상태는 추가하지 않는다.

여행 기록 시트에는 Figma의 `1F JOURNEY`, `2F EMBLEM`, `3F TRY` 카드를 모두 표시한다. 상세 프레임이 제공된 `1F JOURNEY`만 상세 상태로 전환한다. 나머지 카드에는 Figma에 없는 내용을 임의로 만들지 않는다.

## 6. 컴포넌트와 재사용

페이지 전용 구현은 `src/pages/boarding-pass/passport/`에 둔다.

- `PassportPage.jsx`: 라우팅 상태, 단계 이동, 시트 열기와 닫기
- `PassportPage.module.scss`: 여권 레이아웃, 진행 바, 모바일 시트와 반응형 스타일
- `passportData.js`: API로 교체할 정적 화면 데이터
- `PassportPage.test.jsx`: 상태 전환과 사용자 흐름 검증

다음 기존 요소를 재사용한다.

- `BoardingPassChrome`
- `BoardingTicketCard`
- 보딩패스 공통 닫기·이동 화살표 에셋
- 랜딩 배경과 제목 영역
- 기존 색상·폰트·safe-area 토큰
- 기존 티켓 스탬프 에셋

다른 화면에서 사용하지 않는 여권 전용 마크업을 범용 컴포넌트로 추출하지 않는다. 한 페이지 안에서 읽기 어려울 정도로 커질 때만 순수 표현 컴포넌트를 같은 폴더에 분리한다.

## 7. Mock 데이터와 이후 API 교체

이번 작업에서는 `src/shared/api/`와 MSW endpoint를 변경하지 않는다. `passportData.js`가 다음 화면 모델을 제공한다.

- 여권 번호, 영문 이름, 국적, 발급일, 크레딧
- 방문 횟수와 스탬프 날짜 6개
- 최근 방문 매장, 주소, 입장 번호, 비행 시간
- 티켓 표시에 필요한 탑승 정보

컴포넌트는 이 화면 모델만 사용한다. 실제 여권·방문·크레딧 API가 연결될 때 데이터 공급부만 교체한다. 테스트용 Bearer token이나 비밀값은 저장소와 클라이언트 환경변수에 넣지 않는다.

## 8. 에셋 전략

- Figma MCP가 제공한 여권 커버, 열린 여권, 금색 워드마크, 로렐, 보우, 매장 사진과 썸네일을 로컬 에셋으로 저장한다.
- 만료되는 Figma 원격 URL을 코드에 남기지 않는다.
- 장식은 가능한 한 합성 이미지로 사용하고, 이름·국적·날짜·크레딧·방문 정보는 이후 API 교체를 위해 DOM 텍스트로 유지한다.
- 기존 에셋과 같은 파일을 중복 저장하지 않는다.

## 9. 상호작용과 접근성

- 이동 버튼은 실제 `button`과 명확한 `aria-label`을 사용한다.
- 현재 단계는 진행 바의 `aria-valuenow`와 보조 텍스트로 알린다.
- 바텀시트는 휴대폰 프레임 안에 위치하는 `role="dialog"` 영역으로 구현한다.
- 시트가 열리면 첫 조작 요소로 포커스를 이동한다.
- `Escape`, 배경 클릭, 상단 닫기 버튼으로 시트를 닫을 수 있다.
- 시트가 열린 동안 배경의 조작 요소에는 포커스가 이동하지 않도록 한다.
- 동작에 hover만 사용하지 않고 최소 44×44px 터치 영역을 유지한다.
- 추가 애니메이션은 넣지 않고 기존 `prefers-reduced-motion` 정책을 유지한다.

## 11. 테스트와 시각 검증

### 자동 테스트

- 랜딩의 `PASSPORT 확인`이 인증된 사용자를 여권으로 이동시킨다.
- 여권 라우트가 직접 접근으로 렌더링된다.
- 이전·다음 버튼이 25%, 50%, 75%, 100% 상태를 이동한다.
- 첫 이전 버튼과 마지막 다음 버튼이 비활성화된다.
- `제품 보러가기`가 `/products`로 이동한다.
- 여행 기록 시트, 1F 상세, 티켓 시트가 열리고 닫힌다.
- 시트가 열린 상태의 닫기 버튼은 시트만 닫는다.
- 시트가 없는 상태의 닫기 버튼은 랜딩으로 이동한다.
- `비행 종료`가 랜딩으로 이동한다.

### 시각 검증

- Figma `36:5237`, `36:5315`, `36:5409`, `36:5545`, `36:5684`, `36:5824`, `36:5982`, `36:6144`와 390px 캡처를 비교한다.
- 320px와 430px에서 가로 overflow, 잘림, 겹침이 없어야 한다.
- 데스크톱 휴대폰 외형 안에서 바텀시트가 프레임 밖으로 벗어나지 않아야 한다.

### 전체 검증

```bash
npm run verify
```

## 12. 완료 기준

- 두 브랜치의 기존 변경사항이 손실 없이 한 작업 브랜치에 통합된다.
- Figma 48~55 상태가 기존 보딩패스 흐름에서 접근 가능하다.
- 모든 정보가 Mock 화면 모델로 렌더링되며 API 코드에는 새 임시 계약을 추가하지 않는다.
- 신규·기존 자동 테스트와 프로덕션 빌드가 통과한다.
- 320~430px 모바일 너비와 데스크톱 휴대폰 외형에서 화면이 깨지지 않는다.
