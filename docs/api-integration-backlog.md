### 여권 연동 메모

- 신분 정보 수정은 토큰이 있으면 `PATCH /users/me`로 저장하고, 실패하면 시트를 열어 둔 채 사유를 보여 준다. 시트가 열린 사이 401로 토큰이 지워졌으면 지면 표기만 바꾼다. 실서버 저장 반영 확인 완료.
- 여권 라우트는 이제 보호 구간이다 — 비로그인 열람(채움 데이터 데모)은 로그인 유도로 바뀌었다. 채움 데이터는 로그인 상태에서 조회가 실패했을 때의 안전망으로 남는다.
- 생년월일은 `GET /passport` 응답(PassportResponse)에 없어 `GET /users/me`에서 합쳐 온다.
- 방문 스탬프는 받은 그대로 보여 준다 — 0회면 0개. 채움 데이터는 조회가 실패했을 때(비로그인)만 쓴다.
- 여행 기록 면(마지막 면)은 넘겨서 못 가고 **스탬프를 눌러야** 그 방문의 상세(`GET /passport/visits/{id}`)로 열린다. TRAVEL HISTORY·티켓 탑승자/패스코드도 그 방문 값이다.
- TRAVEL HISTORY의 층 카드는 아코디언 — 누르면 그 층 이야기(`GET /floors/{floorId}`)가 카드 아래로 펼쳐지고, 다시 누르면 접힌다.
- TRAVEL HISTORY도 가이드와 같은 규칙으로 **AI 추천 층만 세운다**(추천 표시가 없으면 전체). 각 카드에 ✦ AI 배지 + 펼침 시 추천 사유 한 줄. 방문 상세에는 추천 여부가 없지만 응답의 `boardingPass.boardingPassId`로 그 방문의 동선(`GET /boarding-passes/{id}/route`)을 조회하면 층별 `isRecommended`·`reason`이 남아 있다 — `floorId`로 합친다. 동선은 패스별 저장이라 과거 방문에도 유효하며, 조회가 실패하면 배지 없이 기록만 보여 준다.

## 블로커 (백엔드/인프라 의존)

### 1. Azure 스토리지 CORS 규칙 없음 — ✅ 백엔드 추가 완료 (2026-08-16)

백엔드가 규칙 추가 완료 회신 — Origin은 localhost:5173 + Vercel, Method는 GET/POST/DELETE/PUT/PATCH 전부. 브라우저 업로드(PUT)·결과 저장(GET fetch) 경로 재검증 대기 → "연동 후 재검증" 항목. 단, 재검증은 블로커 5(실서버 전체 401)가 풀린 뒤에나 가능.

### 2. 상품 누끼 컷(투명 PNG) 없음

사진이 색당 1장, 전부 흰 배경 카탈로그 컷 JPEG(총 18장)라 어두운 피팅 카드 위에서 흰 박스가 보인다. multiply 블렌드는 제품 색을 왜곡해(Soft Pink → 갈색) 철회. 시안(배경 없이 제품만)을 살리려면 배경 제거 에셋 필요.

### 3. 층 콘텐츠 시드에 PRODUCT·QUOTE·IMAGE 블록 없음 — 가이드 상품 카드 미표시

실서버 4개 층(`GET /floors/{id}`)의 `contents`가 전부 TEXT·LIST 블록뿐이라, 여행 가이드 피그마 시안(44~47-1)의 층별 상품 카드와 인용구가 화면에 안 나온다. 스웨거 계약(`FloorContentResponse`)에는 `blockType: PRODUCT`와 `product`(productId·name·price·imageUrl)가 이미 있고 **프론트 렌더도 구현 완료** — 시드 데이터만 넣으면 배포 없이 바로 표시된다.

**(a)안 확정 (2026-08-16, 백엔드): 피그마 가이드 상품으로 넣는다.** 백엔드에 전달한 픽스 값 — 상품 카드는 항상 그 층 콘텐츠의 **맨 끝**(기존 마지막 orderNo 다음부터 연번). 피그마(44~47-1) 기준:

| --- | --- | --- | --- | --- |
| JOURNEY | (45) 1F 여정 | 끝+1 | Ottomar 비세토스 트롤리 | ₩2,750,000 |
| JOURNEY | (45) 1F 여정 | 끝+2 | Ottomar 그라데이션 비세토스 위켄더 | ₩2,050,000 — 기존 `productId 6` 재사용 가능 |
| EMBLEM | (46) 2F 상징 | 끝+1 | 뮌헨 비세토스 토트 Cognac | ₩1,290,000 |
| HORIZON | (47) 3F 시도 | 끝+1 | Himmel Shopper in MIRUM® | 피그마에 가격 없음 — 값 필요(카드가 가격을 표시) |
| HORIZON | (47) 3F 시도 | 끝+2 | Ottomar ECONYL®과 가죽이 더해진 위켄더 백팩 | 피그마에 가격 없음 — 값 필요 |

- 3F 두 상품의 피그마 카드는 가격 대신 소재 설명 두 줄인데, 계약(`product`)에 설명 필드가 없어 프론트는 이름+가격으로 그린다. `price`는 아무 값이나 실값으로(누락 시 "₩0"으로 표시됨).
- 층별 인용구(예: "이동의 방식", "비대칭과 마름모가 완성한 아이콘")도 `QUOTE` 블록으로 추가 요청 — 유지.

### 4. 카카오 로그인 — 백엔드 토큰 교환 401 (보류, 2026-08-16)

증상: 카카오 인가 → code 수신까지 정상, `POST /auth/kakao`가 401 `KAKAO_AUTH_FAILED`. 실패 지점은 백엔드 ↔ 카카오 토큰 교환(`POST kauth.kakao.com/oauth/token`)으로, 브라우저에는 보이지 않는 서버 간 구간이다.

프론트 쪽 확인 완료:

- REST API 키는 **백엔드 앱과 같은 키** 사용 (프론트 `.env` = 백엔드 앱)
- 그 앱 콘솔에 `http://localhost:5173/auth/kakao/callback` 등록됨 — 인가 URL 직접 호출로 확인(KOE006 없음)
- 요청은 스웨거 계약대로 `{code, redirectUri}` 전송, StrictMode 이중 교환 가드 있음
- 백엔드는 client_secret 사용 중이며, 교환 시 **요청 본문의 `redirectUri`를 사용**한다고 확인(2026-08-16) — redirect_uri 불일치 후보 제거

백엔드 확인 대기 — 남은 후보는 사실상 하나:

1. **client_secret 값** — 재발급 후 미갱신/오타면 카카오가 `invalid_client`로 거절. **백엔드 로그의 카카오 응답 본문(KOE 코드) 확인이 마지막 관문**이다. 로그 없이 더 좁힐 방법이 없다

**직접 교환 실험으로 확정 (2026-08-16, 백엔드 수정 후 재발 확인 뒤):**

실제 인가 code를 캡처해 같은 `client_id`·같은 `redirect_uri`로 카카오 토큰 엔드포인트에 시크릿 없이 직접 교환 → **`401 KOE010 invalid_client "Bad client credentials"`**.

- 이 앱은 **시크릿 검사가 켜져 있고**, 자격(시크릿)만으로 거절된다 — code·키·redirect_uri는 전부 유효하다는 뜻
- 따라서 백엔드의 401도 카카오의 KOE010일 가능성이 지배적. 백엔드가 확인할 것:
  ① 콘솔 [보안] 탭의 client_secret 값과 서버 설정값이 **문자 그대로 일치**하는지(재발급 이력 주의)
  ② token 요청 본문에 `client_secret` 파라미터가 **실제로 실리는지**(설정 키 이름 오타로 빈 값이 나가는 경우가 흔함)
  ③ `client_id`가 콘솔의 REST API 키(`b9423f…`)와 동일한지

### 5. 실서버 전체 401 — 부분 빌드 배포 중 ⚠️ (2026-08-16 오후 발견)

`/auth/login`·`/auth/signup` 포함 **모든 API가 401 `{"message": "인증이 필요합니다."}`**. 원인은 프론트가 아니라 배포 상태: 라이브 `/v3/api-docs`에 경로가 5개뿐(`/floors`, `/floors/{id}`, `/surveys/questions`, `/fitting-sessions/upload-url`, `/users/me/body-image`)이고 **`/auth`가 아예 없다**. 전역 JWT 보안은 켜져 있는데 토큰을 받을 수단이 없어 전부 401이 된다. 백엔드가 시드 작업 중 부분 빌드를 배포한 것으로 보임 — 정상 배포 회복을 기다렸다가 로그인·가이드 재검증.

### 6. 문서·실서버 불일치

- 피팅 `creditCost`: 문서 50 ↔ 실서버 100
- `GET /passport` 응답에 `birthDate` 없음 — 프론트는 `/users/me` 병합으로 대응 완료. 백엔드가 추가해 주면 병합 호출 하나를 줄일 수 있다
- `docs/api` 명세가 중복본이 있고 일부 낡음 → **계약 기준은 라이브 Swagger(`/v3/api-docs`)로 통일**

## 참고 — AI 피팅 구현 방식 (질문 대응용)

**폴링 방식. 결과 조회 요청 하나를 열어두는 long-polling이 아니다.**

```
[사진 선택 시]  POST /fitting-sessions/upload-url → Azure Blob PUT → fileKey
[사진 미선택]   fileKey 생략 → 회원 기본 전신 이미지 사용
                     ↓
POST /fitting-sessions (productColorId, fileKey?)  ← 1회 호출
  → 즉시 PENDING + fittingSessionId, 크레딧 차감(실서버 100)
                     ↓
GET /fitting-sessions/{id}  ← 2초 간격 폴링 (setInterval, 매번 새 요청)
  DONE   → 폴링 중단, resultImageUrl로 결과 화면 전환
  FAILED → 폴링 중단, 업로드 화면 복귀 + 환급 안내(백엔드 자동 환급)
```

- 피팅 열쇠는 상품이 아니라 색(`productColorId`). 상세의 Fitting 링크가 보고 있는 색을 쿼리로 싣는다: `/products/1/try-on?color=2`
- 진행률 바는 장식 — 서버가 끝내기 전에는 95% 천장 아래에서만 차오르고, 100%는 서버 `DONE`만 채운다
- 조회 실패 1회로 폴링을 끊지 않고 다음 눈금에 재시도. 401만 즉시 중단
- 취소/화면 이탈 시 인터벌 해제 + 요청 abort
- 실패 사유는 백엔드 message 그대로 표시 (`INSUFFICIENT_CREDIT` 등)

실서버 검증: 업로드 URL→Azure PUT 201(curl), 세션 생성→폴링→FAILED→화면 복귀, 크레딧 원장 `FITTING -100 → REFUND +100`, 잔액 표시.
